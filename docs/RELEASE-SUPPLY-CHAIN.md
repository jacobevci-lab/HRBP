# Release supply-chain assurance

HRBP One release evidence is generated from the exact reviewed Git commit and is intended to make on-prem customer releases independently traceable.

## Pull request gates

The `Security Assurance` workflow runs on every pull request to `main` and on every push to `main`.

It performs:

- production and full npm dependency audits,
- a CycloneDX production dependency SBOM generated by npm,
- deterministic source archiving from the exact checked-out commit,
- SHA-256 digests for the source archive, SBOM, package/lock files, on-prem Docker inputs and every committed Prisma migration,
- release-evidence validation that fails if the checked-out revision, migration inventory or hashes drift,
- secret-value leakage checks against configured HRBP/database service credentials,
- CodeQL JavaScript/TypeScript analysis with the extended security query suite.

The generated evidence bundle contains:

- `hrbp-one-source.tar`
- `hrbp-one.cdx.json`
- `release-manifest.json`
- `SHA256SUMS`

Generated evidence is never committed back into the repository.

## Main-branch attestations

For a successful push to `main`, GitHub's artifact attestation service signs:

1. build provenance for the exact source archive, and
2. the CycloneDX SBOM bound to that same source archive.

The attestation job runs only after the release-evidence job has passed. It uses short-lived GitHub OIDC credentials and does not require a long-lived signing key in repository secrets.

The source archive is created with `git archive`, so it contains tracked files from the reviewed revision only. Untracked runner files, local environment files, generated build folders and customer secrets are outside the archive.

## Evidence boundary

The release manifest is intentionally limited to non-secret release metadata:

- full Git revision,
- Node/npm toolchain versions,
- artifact sizes and hashes,
- hashes of package/deployment inputs,
- hashes and paths of committed Prisma migrations.

Environment variables, database URLs, passwords, service tokens, SMTP credentials, OIDC secrets and tenant/employee data must never appear in the SBOM or manifest. The validator checks configured sensitive values and fails if one appears in generated evidence.

## Customer verification

A customer or release operator can verify the downloaded evidence locally:

```bash
sha256sum -c SHA256SUMS
```

The GitHub attestation can then be verified against the repository identity with GitHub CLI tooling where supported. Verification should be performed against the exact approved release revision; a valid attestation does not replace deployment postflight, database migration checks, malware-scanner health or customer acceptance testing.

## Scope and limitations

This control establishes source/SBOM integrity and repository-backed provenance. It does not by itself prove reproducible container bytes, sign external customer container registries, replace vulnerability management, or guarantee that a customer built an image from the attested source. If HRBP later distributes prebuilt OCI images, the release process should additionally attest and sign the pushed image digest and attach the SBOM to that digest.
